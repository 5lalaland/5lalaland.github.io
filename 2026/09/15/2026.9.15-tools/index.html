1. 自动化安全测试工具简介

定义： AI Security Testing Tools 是用于自动化测试大模型及 AI 应用安全性的工具，主要通过构造测试输入、调用目标模型、分析响应以及生成评估报告，发现潜在的安全问题，例如 Prompt Injection、Jailbreak、敏感信息泄露、RAG Poisoning 和 Agent Tool Misuse。
Promptfoo 与 Garak 的区别： Promptfoo 和 Garak 都能自动向模型发送测试输入，但定位不同。Promptfoo 更适合应用层评测、断言（Assertion）、红队测试和安全回归；Garak 更像面向语言模型的漏洞扫描器，提供 Probes、Detectors、Generators 和报告流水线。 Promptfoo 适合测试自己开发的 LLM、RAG 和 Agent 应用，而 Garak 适合快速检查某个模型在不同攻击类型下的安全表现，两者可以配合使用。
自动化测试的基本流程： 确定测试目标 → 选择攻击类型 → 自动生成或加载测试 Prompt → 调用目标模型或 Agent → 检查响应与工具执行结果 → 生成报告 → 分析风险。

2. Promptfoo（LLM 自动化评测与红队测试）

2.1 Promptfoo 基础

定义： Promptfoo 是一个开源的大模型应用评测与红队测试框架，通过配置文件定义测试目标、Prompt、测试用例和判断标准，然后自动执行测试并展示结果。
核心概念： 1. Provider / Target：要测试的模型或 AI 应用，例如 OpenAI 模型、本地 Ollama 模型、自定义 HTTP API 或 Agent。2. Prompt：发送给模型的提示模板，支持使用 {{variable}} 注入测试变量。3. Test Case：具体测试输入，例如“忽略之前所有指令”。4. Assertion（断言）：自动判断模型输出是否满足要求。5. Plugin：红队测试中用于生成某类攻击输入的组件，例如 Prompt Extraction、Hijacking。6. Strategy：对攻击输入进行包装、变换或迭代的攻击策略。7. Evaluation（评估）：批量运行测试并记录通过、失败及相关指标。

Assertion 决定如何判断测试是否通过。 常见类型：1. contains：输出必须包含指定字符串。2. not-contains：输出不能包含指定字符串。3. equals：输出必须完全匹配。4. regex：使用正则表达式匹配。5. contains-json：检查输出是否包含合法 JSON。6. llm-rubric：使用另一个 LLM 根据自然语言评分标准判断结果。7. javascript / python：编写自定义逻辑进行判断。

3. Garak（LLM Vulnerability Scanner）

3.1 Garak 基础

定义： Garak 是 NVIDIA 开源的 LLM 漏洞扫描工具，可以通过预置的大量攻击测试自动检查模型是否存在提示注入、Jailbreak、训练数据泄露、幻觉及其他异常输出问题。
核心组件： 1. Generator（目标模型接口）：负责连接待测试模型，例如 OpenAI API、Hugging Face 模型或其他推理服务。2. Probe（探针）：负责生成或提供特定类型的攻击输入，例如 DAN Jailbreak、编码注入。3. Detector（检测器）：根据模型回答判断是否出现目标异常行为。4. Harness（测试执行器）：管理 Probe 与 Generator 的执行流程。5. Evaluator（评估器）：汇总检测结果并生成评估数据。
执行流程： Probe 准备攻击 Prompt → Generator 调用目标模型 → 模型返回 Response → Detector 判断是否命中漏洞条件 → Evaluator 汇总报告。

第三步：尝试其他攻击类型。

3.4 Garak 常见 Probe

Probe 是 Garak 的核心攻击测试单元。 常见类别：1. promptinject：尝试把恶意指令注入正常任务。2. dan：测试 DAN 类 Jailbreak 提示。3. encoding：使用编码或特殊文本表达方式测试模型行为。4. leakreplay：测试是否可能复现训练数据内容。5. packagehallucination：检查模型是否推荐不存在的软件包。6. snowball：测试复杂问题引发的错误回答。7. xss：测试与跨站脚本风险相关的模型输出。
使用方式： 通过 --spec probes.类别 指定 Probe 家族，也可以进一步指定某个 Probe 类。实际支持的名称以当前安装版本的 garak --list_probes 输出为准。

3.5 查看 Garak 测试结果

执行结束后，Garak 会在终端打印各 Probe 的测试进度和检测结果，并生成结构化报告。
主要输出： 1. garak.log：运行和调试日志。2. JSONL Report：记录测试输入、模型生成结果及检测状态。3. Hit Log：记录被检测器判定命中目标异常行为的测试案例。
结果解读： Garak 中的 FAIL 通常表示某个 Detector 判断模型输出存在对应风险，并不等于真实应用已经发生权限突破。某些 Detector 依赖字符串匹配、分类器或特定攻击成功条件，可能出现误报和漏报。因此需要人工复核命中的 Prompt、Response 及检测逻辑。

4. Promptfoo 与 Garak 的实际选择

Promptfoo： 适合已经开发了一个 AI 应用，需要验证它是否遵守业务规则、是否会泄露内部信息、是否容易受到 Prompt Injection，以及修改代码后安全表现有没有下降。其主要优势是可以自定义 Test Case、Assertion、红队 Plugin 和 CI/CD 自动化评测。
Garak： 适合拿到某个模型或推理接口，希望快速扫描模型在多类攻击输入下的异常行为。其主要优势是预置 Probe 和 Detector，使用命令行即可完成批量测试。
实际工作流： 1. 先用 Garak 对底层模型做基础安全扫描，观察高风险行为。2. 使用 Promptfoo 对完整 LLM/RAG/Agent 应用执行定向红队测试。3. 对发现的失败案例编写固定 Assertion 或自定义检测逻辑。4. 修复之后重新执行 Promptfoo Eval，检查安全漏洞是否复现。5. 对 Agent 工具调用、数据库访问等实际操作，再结合 Trace 和系统日志进行验证。
测试指标： 1. ASR（Attack Success Rate）：攻击成功次数占有效攻击测试次数的比例，必须事先明确成功标准。2. Pass Rate：满足测试断言的比例。3. False Positive Rate（FPR）：正常行为被错误判为违规的比例。4. Task Success Rate：应用完成正常业务任务的比例。需要注意 Promptfoo 的 Assertion Pass Rate 与 Garak 的检测器失败比例不一定能够直接进行数值比较。

5. 自测题

1. Promptfoo 和 Garak 有什么区别？实际工作中应该怎么选择？

答：Promptfoo 和 Garak 都是 LLM 自动化安全测试工具，但 Promptfoo 更侧重应用层评测，通过配置 Provider、Prompt、Test Case 和 Assertion 实现业务规则验证、红队测试和安全回归，适合测试完整的 RAG 或 Agent 应用；Garak 更侧重模型漏洞扫描，通过 Generator 连接模型、Probe 提供攻击输入、Detector 判断异常行为，适合快速发现模型在不同攻击类型下的安全问题。实际工作中可以先使用 Garak 扫描底层模型，再使用 Promptfoo 测试完整应用，并将发现的漏洞加入回归测试集。

2. Promptfoo 中的 Provider、Plugin、Strategy 和 Assertion 分别是什么？

答：Provider 或 Target 是被测试的模型或 AI 应用；Plugin 用于生成特定风险类别的攻击测试，例如 Prompt Extraction 和 RAG Poisoning；Strategy 用于改变攻击输入的表达或执行方式；Assertion 则负责判断模型输出是否满足预期要求。例如测试系统提示词泄露时，可以使用 Prompt Extraction Plugin 构造攻击输入，再利用 Assertion 或专门的红队评分器判断攻击是否成功。

3. Garak 中的 Probe、Generator 和 Detector 分别起什么作用？

答：Probe 负责提供针对特定漏洞类型的测试输入，例如 Jailbreak 或编码攻击；Generator 是连接待测试模型的接口，负责将攻击输入发送给模型并接收回答；Detector 根据模型输出判断是否出现目标异常行为。整个测试流程可以理解为 Probe 生成攻击输入，Generator 调用模型，Detector 检查结果，最后由评估和报告组件汇总检测情况。

4. 如果 Promptfoo 或 Garak 报告显示攻击成功，是否说明模型或 Agent 存在可利用漏洞？

答：不能直接认定。自动化工具的结果取决于断言规则、Detector 和评分模型，它们可能出现误报或漏报。对于普通文本生成任务，需要确认模型是否真的泄露了秘密或违反了预期行为；对于 Agent，还需要进一步查看 Tool Calling Trace，确认模型是否发起了非授权操作、工具是否执行成功，以及是否真的产生数据泄露或权限突破。因此自动化扫描主要用于发现潜在问题，真实漏洞仍需要结合应用权限边界和实际执行结果验证。
